# Question 2: Four-node production pipeline (solution)

**In short.** The main fix (**v1**) keeps the four nodes `triage → retrieve → compose → audit` but makes **only compose call the LLM**. Triage, retrieve and audit become code. That takes a ticket from about **73,400 to about 1,460 points**, well under the 2,500 target. One further optimization, **v2**, strips formatting from the retrieved articles and shortens the compose instruction, reaching about **1,380 points**. **v2 is the graded version.** Measuring the remaining options shows that cutting further would risk wrong answers the simulator cannot detect (§4.4).

| Ticket | Path | Baseline | v1 (main fix) | **v2 (graded)** |
|---|---|---:|---:|---:|
| T-1001 | REFUND | 73,428 | 1,557 | **1,473** |
| T-1002 | SEND_ARTICLE (denial) | 73,485 | 1,464 | **1,380** |
| T-1003 | ESCALATE_TIER2 (escalation) | 73,257 | 1,428 | **1,344** |
| T-1004 | REPLACE (physical fulfillment) | 73,488 | 1,389 | **1,305** |
| **Average (public)** | | **73,415** | **1,460** (−98.0%) | **1,376** (−98.1%) |
| T-1091 (holdout) | SEND_ARTICLE | n/a | 1,431 | **1,347** |

Both versions give the correct `action` and `kb_article` on every ticket, including T-1091.

## 1. Question

> **Product:** ShopAssist, with the same routing as Question 1, implemented as **triage → retrieve → compose → audit** in `question2/agent.py`.
> The help center in this track is much larger than in Question 1 (`shared/kb.py`). The baseline pipeline is correct on the public tickets in `pytest`.
> Reduce **points per ticket** under the same billing rules. Graded fields: `action`, `kb_article`.
> **Target:** ≤ **2,500** points per public ticket (T-1001–T-1004).
> **Submit:** changes to `agent.py`, a points breakdown for two tickets (one physical fulfillment path, one denial or escalation path), and a short write-up.

Billing (same as Q1): `points = uncached_input × 3 + cached_input × 0.3 + output × 15` (cached = identical prefix ≥ 1,024 tokens).

## 2. Inference from the Question (Understandings)

**How the baseline spends its points (T-1001: 73,428 points):**

| Node | Input tok | Output tok | Points | Why it is so expensive |
|---|---:|---:|---:|---|
| triage | 8,456 | 484 | 32,628 | Sends `help_center[:120_000]` (mostly filler) and a random `trace-{uuid}`; "step by step" triggers a long answer |
| retrieve | 592 | 46 | 2,466 | Asks the LLM to "print full text" of articles that code could just look up |
| compose | 1,187 | 487 | 10,866 | Sends the triage text **twice**; "full reasoning" triggers a long answer |
| audit | 6,716 | 488 | 27,468 | Re-sends `help_center[:80_000]` and everything else; "double-check / restate" triggers a long answer |
| **Total** | | | **73,428** | 4 LLM calls, about 1,950 output tokens |

**What the "much larger help center" really is** (`shared/kb.py::expanded_help_center_blob`): the same **5 policy articles as Q1 (about 155 tokens)**, padded to over 210,000 tokens with repeated `## Internal routing note` chunks. Those chunks say of themselves that they *do not change customer policy unless an article id is cited*. So **about 0.07% of the help center is policy**.

**What the simulator does** (`shared/llm.py`), same as Q1:
- Every LLM call must contain `ORDER_SNAPSHOT: {…} END_SNAPSHOT`, or it raises an error.
- Every call returns the decision JSON. That is 36–46 tokens in short mode (**540–690 points of output per call, whatever the prompt asks for**), and 480+ tokens if the prompt contains a trigger phrase.
- It decides from the order snapshot alone and **never reads the articles**. This matters in §4.4.

**The key consequence: the number of LLM calls sets the cost floor.**

| LLM calls per ticket | Output floor | Measured with a minimal input | Fits ≤ 2,500? |
|---:|---:|---:|:-:|
| 4 (baseline shape) | 2,160–2,760 | n/a | ✗ never |
| 2 (LLM triage + compose) | 1,080–1,380 | 1,860–2,217 | ✓ (11% margin) |
| **1 (compose only)** | **540–690** | **1,389–1,557** | **✓ (38% margin)** |

**When does an LLM triage pay off?** An LLM triage call costs about 950–1,100 points (its output floor plus its input). Its only benefit is that compose then receives fewer articles: going from 5 to 1 saves about 120 tokens, or **~360 points**. So the triage call **loses about 600–700 points per ticket**. It only pays off once retrieval can remove more than about **330 tokens** of policy per ticket, and here the policy is about 155 tokens in total. So triage and retrieve are **code**, and the LLM is used once, where judgment is needed: compose.

**Constraints:**
- Keep the four nodes `triage → retrieve → compose → audit`, as methods in this order.
- `action` and `kb_article` stay correct for T-1001 to T-1004 (graded) and T-1091 (same product, so tested here too).
- No import of `eval/reference.py`, and no decisions made in Python. Code nodes prepare inputs and validate outputs, and the LLM decides.
- No padding to reach the cache threshold. Every prompt is under 1,024 tokens.
- `test_help_center_exceeds_context` is unchanged. It is a fact about the data, not about the agent.

## 4. How are we trying to achieve (Approach)

### 4.1 Main solution: v1 (one LLM call; triage, retrieve and audit as code)

| Node | Baseline | v1 | Points |
|---|---|---|---:|
| **triage** | LLM over 120k chars of help center | **Code.** Builds the ticket brief: the customer's own messages and the order's decision fields as compact JSON (no `order_id`, `sku` or `title`), inside the snapshot markers. It reuses Q1's `ticket_brief()`. | 0 |
| **retrieve** | LLM "prints" 8 articles | **Code.** Pulls the policy articles from the KB index (`article_ids()` / `load_article()`), body text only. The routing-note filler has no article id and is never retrieved. | 0 |
| **compose** | LLM with triage twice and full reasoning | **The only LLM call.** The system prompt has the allowed actions, the retrieved articles and "JSON only, 1-sentence reply". The user message is the brief. No trigger phrases and no random ids. | 1,389–1,557 |
| **audit** | LLM re-reads 80k chars | **Code guardrail.** Accepts the draft only if `action` is one of the 4 allowed actions and `kb_article` is a retrieved article. Otherwise it **hands the ticket to a human**: `ESCALATE_TIER2` (keeping `kb_article` if it is valid, else `""`). Unparseable output also escalates. | 0 |

**It is still a real pipeline.** Each node keeps its job and its order. The audit is stricter than the baseline's, because it can't be talked into an unknown action or a made-up article, and it costs 0 points.

**The articles are retrieved, not rewritten as a rule table (unlike Q1 v3).** Q2 is about working from a large help center. Using the KB's own text means a changed or added article is picked up automatically, with nothing hand-written to drift.

### 4.2 Further optimization: v2 (leaner compose prompt)

After v1, everything left is in the single compose call (T-1001: 46 output tokens = 690 points, which is fixed; 289 input tokens = 867 points).
1. **Strip Markdown from the retrieved articles (154 → 143 tokens, −33 points).** `**not eligible**` becomes `not eligible`. Every word is kept and only formatting goes.
2. **Shorter compose instruction (60 → 43 tokens, −51 points):**
   `Actions: REFUND, REPLACE, SEND_ARTICLE, ESCALATE_TIER2 (if no article fits). Cite the backing article. JSON only: action,kb_article,customer_reply (1 sentence).`
   It still lists all allowed actions, the fallback, the citation and the one-sentence reply.

### 4.3 Saving per change (measured)

| Step | Version | T-1001 | T-1002 | T-1003 | T-1004 | T-1091 |
|---|---|---:|---:|---:|---:|---:|
| Baseline (4 LLM calls) | | 73,428 | 73,485 | 73,257 | 73,488 | n/a |
| 1 LLM call; triage, retrieve and audit as code | **v1** | 1,557 | 1,464 | 1,428 | 1,389 | 1,431 |
| + Markdown stripped from articles | | 1,524 | 1,431 | 1,395 | 1,356 | 1,398 |
| + shorter compose instruction | **v2** | **1,473** | **1,380** | **1,344** | **1,305** | **1,347** |

### 4.4 Limits: why it stops at v2

Every option beyond v2 was measured (avg = the 4 public tickets; all 5 tickets checked):

| Option beyond v2 | Avg points | vs v2 | Simulator says correct? | Correct article in the prompt for all 5? |
|---|---:|---:|:-:|:-:|
| v2 | 1,376 | n/a | ✓ | ✓ |
| Ultra-short instruction (drops the fallback hint and "Cite…") | 1,346 | −30 | ✓ | ✓ |
| Keyword top-4 retrieval | 1,289 | −87 | ✓ | ✓ (worst case: 3rd of 4 kept) |
| Keyword top-3 retrieval | 1,196 | −180 | ✓ | ✓ (T-1003 at the edge) |
| Keyword top-2 retrieval | 1,106 | −270 | ✓ | **✗: the correct article is dropped** |
| Floor: order data only (no policy, no customer text, no instruction) | ~720 | n/a | n/a | n/a |

**Top-2 retrieval is the evidence.** It removes the correct article from the prompt for some tickets, yet the simulator still marks every answer correct, because it never reads the articles. So **the tests cannot detect retrieval mistakes**. Any saving from retrieving less is a risk only a real model would expose. With a simple keyword ranker, T-1003's correct article already ranks only 3rd of 5.

The one safe option (the ultra-short instruction) saves 30 points (2%) by removing guidance the model gets for free today. That is not worth weakening the prompt.

**Also considered and rejected:**

| Idea | Result | Why not |
|---|---|---|
| Keep 4 LLM calls, just trimmed | ≥ 2,160 points of output alone | Can't reliably fit 2,500 |
| LLM triage + LLM compose | 1,860–2,217 | Works, but the triage call costs ~1,000 to save ~360 (§2) |
| Hand-written rule table (Q1 v3 style) | ~−250 pts | Drifts from the KB, which defeats Q2's retrieval point |
| Pad prompts to 1,024 tokens for the cache price | n/a | Works only because the simulator doesn't check the prefix was sent before |

### 4.5 Risks
- **Retrieval returns every policy article.** That is right at about 145 tokens, but a much larger real KB needs top-k ranking. A `ponytail:` comment in `_retrieve` marks the ~330-token break-even.
- **A customer could write a trigger phrase** (as in Q1), giving one long answer of about +6,700 points. On a real API, a `max_tokens` cap prevents it.
- **The audit escalates with `kb_article=""`** when the model names an unknown article. That is safe for the customer, but it would fail grading for that ticket. It never happens with the simulator, and `test_audit_guardrail` covers it.

## 5. Implementation (Code)

### 5.1 [question2/agent.py](../question2/agent.py): v2 graded, v1 kept as a subclass

```python
from __future__ import annotations

from dataclasses import dataclass

from shared.billing import CostSession
from shared.kb import article_ids, load_article
from shared.llm import ChatMessage, LlmClient

from question1.agent import parse_resolution, ticket_brief

ACTIONS = ("REFUND", "REPLACE", "SEND_ARTICLE", "ESCALATE_TIER2")

# No reasoning/verbosity asks anywhere: output tokens cost 5x input.
COMPOSE_V1 = (
    "Pick an action (REFUND, REPLACE, SEND_ARTICLE, ESCALATE_TIER2) and the kb_article "
    "that backs it, using only these articles; none fits -> ESCALATE_TIER2. "
    "JSON only: action,kb_article,customer_reply (1 sentence).\nARTICLES:\n"
)
COMPOSE_V2 = (
    "Actions: REFUND, REPLACE, SEND_ARTICLE, ESCALATE_TIER2 (if no article fits). "
    "Cite the backing article. JSON only: action,kb_article,customer_reply (1 sentence).\n"
)


@dataclass
class TicketResolution:
    action: str
    kb_article: str


class SupportPipeline:
    """Same product as Question 1 — triage, retrieve, compose, audit (v2, graded).

    Only compose calls the LLM: each call costs >= ~600 points of output, more than
    the whole policy text it could save. Triage, retrieve and audit are code.
    """

    INSTRUCTIONS = COMPOSE_V2
    STRIP_MARKDOWN = True

    def __init__(self, session: CostSession | None = None):
        self.session = session or CostSession()
        self.llm = LlmClient(self.session)

    def handle_ticket(self, ticket_id: str) -> TicketResolution:
        brief = self._triage(ticket_id)
        articles = self._retrieve()
        draft = self._compose(brief, articles)
        return self._audit(draft, articles)

    def _triage(self, ticket_id: str) -> str:
        """Code: the facts compose needs — customer's words + decision fields."""
        return ticket_brief(ticket_id)

    def _retrieve(self) -> dict[str, str]:
        """Code: policy articles only; the ~210k tokens of routing notes carry no policy."""
        # ponytail: returns every policy article (~145 tokens); add top-k ranking once
        # policy text passes ~330 tokens/ticket, the point where an LLM triage pays for itself
        articles = {aid: load_article(aid).split("\n", 1)[1].strip() for aid in article_ids()}
        if self.STRIP_MARKDOWN:  # formatting only; the words are unchanged
            articles = {a: b.replace("**", "") for a, b in articles.items()}
        return articles

    def _compose(self, brief: str, articles: dict[str, str]) -> str:
        system = self.INSTRUCTIONS + "\n".join(f"{a}: {b}" for a, b in articles.items())
        return self.llm.chat(
            "compose", [ChatMessage("system", system), ChatMessage("user", brief)]
        )

    def _audit(self, draft: str, articles: dict[str, str]) -> TicketResolution:
        """Code guardrail: a known action backed by a retrieved article, else a human."""
        try:
            r = parse_resolution(draft)
        except (ValueError, KeyError):  # no JSON / bad JSON / missing field
            return TicketResolution("ESCALATE_TIER2", "")
        kb = r.kb_article if r.kb_article in articles else ""
        if r.action not in ACTIONS or not kb:
            return TicketResolution("ESCALATE_TIER2", kb)
        return TicketResolution(r.action, kb)


class SupportPipelineV1(SupportPipeline):
    """v1: the original compose instruction, Markdown kept in articles."""

    INSTRUCTIONS = COMPOSE_V1
    STRIP_MARKDOWN = False


VERSIONS = {"v1": SupportPipelineV1, "v2": SupportPipeline}
```

Removed from the baseline: `uuid`, `expanded_help_center_blob`, `title_index`, three of the four LLM calls, every trigger phrase, and the duplicated triage text. `ticket_brief()` is shared with Q1 (see [Q1.md §5.2](Q1.md#52-v2-and-v3-the-current-code-in-question1agentpy)).

### 6.5 Write-up

The baseline made 4 LLM calls per ticket. Two of them re-read up to 120k characters of a help center that is 99.9% filler, and all four were told to reason at length, for a total of about 73,400 points per ticket.

Two facts set the design. First, every LLM call costs at least 540–690 points of output, whatever the prompt says, so four calls can never fit the 2,500 target. Second, the real policy is 5 short articles (about 155 tokens), so an LLM triage step to narrow it down would cost about 1,000 points to save about 360.

**The main fix (v1)** therefore keeps the four nodes, but runs three of them as code. Triage builds a compact ticket brief. Retrieve pulls the policy articles out of the help center and skips the filler. Audit is a zero-cost guardrail that escalates anything not backed by a known action and a retrieved article. The one LLM call, compose, gets only what it needs to decide: 1,389–1,557 points, a 98% cut.

**The further optimization (v2)** stripped Markdown from the retrieved articles and rewrote the compose instruction as a compact list, saving 84 points on every ticket (T-1004: 1,389 → 1,305).

Going beyond v2 means retrieving fewer articles, and that was measured and rejected. The simulator ignores the articles, so it marked every answer "correct" even when the correct article was missing from the prompt. A real model would get those tickets wrong. The final, graded version (v2) costs **1,305–1,473 points per ticket, 98.1% below the baseline**, with the same answers on every ticket.
